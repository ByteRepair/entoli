# The menu bar on macOS and iPadOS

`entoli_menu` is the adapter for the platform's own menu bar. The core's port
is `MenuBarHost` (`packages/entoli_core/lib/model/menu_bar.dart`): menus as
data, each item an id, a title, its keys, whether it is enabled and an SF
Symbol, and the id of the item picked back. `nativeMenuBar()` is the whole of
what the app reaches; `main` makes one per process, since it answers the
platform's channel, and hands it to `HostAppMenus` (`lib/app/app_menus.dart`)
on the two Apples. Every other platform has no bar and binds `NoAppMenus`.
What the menus say is the app's — see "The menu bar" in `lib/ui/AGENTS.md`.

One Swift source draws it for macOS and iPadOS (`sharedDarwinSource`), over a
Pigeon contract: `pigeons/menu.dart`, both ends generated by
`tool/prepare.sh` into `lib/src/` and `darwin/.../Contract/`, neither
tracked. Dart sends the whole bar, titled and greyed, and only when what it
says changed; Swift sends back the id of the item picked. A send that fails
gets a `[menu]` line.

The bar is SwiftUI's — `AppCommands`, in each Runner's `.commands` — so the
platform puts in what it always does (Hide, Quit, Full Screen, the Window
menu) and a menu's role says where the app's items go: the app menu, File,
View and Help take them into the platform's own, and an `own` menu is one of
the app's. Each item holds its keys as a keyboard shortcut, so the menu runs
them and Flutter's key handler stands down for them.

Two SwiftUI traps, both from Dart's menus arriving after launch. A `Window`
app's File menu is made only if its group has something in it when the bar is
first built, so a blank item holds the place until Dart sends. And SwiftUI
fills a menu when it is opened, while a shortcut finds only what is filled,
so a key-down monitor fills them all before every ⌘ chord; without it no
shortcut fires until its menu has been opened once.
